**百分位口径**：JMeter HTML 的 `statistics.json` 在高偏态样本下使用近似聚合，和 JTL 全量样本不一致。例如 detail 1200 QPS 那一轮 HTML P95=267ms，JTL 全量 P95=146ms，但两者样本数和均值完全一致。为满足“真实 P95/P99”的要求，本文所有 P90/P95/P99 都用 JTL 全部样本重新计算（nearest-rank）；HTML 报告仅作原始产物保留。`-Qps` 是目标值，实际吞吐以 JTL 样本数/实际时间窗计算。

**稳定/拐点判定**：

- 读/内部校验资源：实际吞吐 ≥ 目标 95%，Error%=0，超时=0，P95 ≤ 200ms。
- 报名链资源：实际吞吐 ≥ 目标 95%，Error%=0，超时=0，P95 ≤ 500ms（报名链包含 user Feign、training 内部校验）。
- 稳定区间取拐点前最后一个未出现数量级延迟跃升的点；拐点取吞吐不再增长或 P95 明显越界的点。

### 5.5 Sentinel Enabled 首轮暴露的 Block 日志风暴

01:39:44 首次用最终阈值跑 detail 1200 QPS（Topology A，直连 8082，200 线程）时出现异常：

- 41,344 样本：200=22,396，429=6,870，503=5,165，连接异常=6,912，超时=1；总吞吐 695.7，Error% 45.83%。
- training-service 日志 60 秒增长 74MB，`Sentinel blocked request` 12,077 条。
- 根因：四个 blockHandler 对每个 Block 都以 WARN 打印 `BlockException` 的完整堆栈；高频 Block 下日志 I/O 和异常构造拖垮服务，出现连接拒绝和 503 级联。

已做最小修复（不改业务逻辑）：WARN 只保留 traceId/资源/ID/Block 类型一行摘要，Throwable 降到 DEBUG 保留堆栈；涉及 `TrainingController`、`InternalTrainingController`、`EnrollmentController`、`SentinelGatewayConfig`。重新构建并重启后，01:46:56 同一 1200 QPS 测试恢复到：58,445 样本、200=42,602、429=15,843、0×503、0 连接异常、0 超时，总吞吐 983.4，成功 716.8/s，成功 P95 391ms / P99 820ms；日志 12.8MB、15,843 条一行 WARN。服务未再出现连接拒绝。
